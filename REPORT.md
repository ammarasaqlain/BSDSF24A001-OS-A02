What is the crucial difference between the stat() and lstat() system calls? In the context of the ls command, when is it more appropriate to use lstat()?
The core difference is how they handle symbolic links. stat() follows the link and returns the metadata of the target file it points to. lstat() intercepts the link and returns the metadata of the symbolic link itself. For the ls command, lstat() is strictly required. If a user runs ls -l, they expect to see the properties of the actual link sitting in that directory, not the original file hiding somewhere else on the system.

Explain how you can use bitwise operators (like &) and predefined macros to extract permission information.
The st_mode field is a bitmask—a single integer where specific binary bits act as on/off switches for different file properties. Predefined macros like S_IRUSR are just integer constants with one specific bit flipped to 1. By using the bitwise AND operator (&) between st_mode and the macro, you isolate that single bit. If the result is non-zero (True), it means that exact permission is enabled. If it is zero (False), the permission is disabled. You run this check sequentially for the owner, group, and others across read, write, and execute bits

Explain the general logic for printing items in a "down then across" columnar format. Why is a simple single loop through the list of filenames insufficient for this task?
A single loop prints sequentially from left to right (row-major order). To print "down then across" (column-major order), the program must calculate the entire grid geometry first based on the terminal width. It uses nested loops (rows, then columns) and calculates the exact 1D array index for each grid slot using the formula row + (column * total_rows). This pulls non-sequential files from the array to artificially construct vertical columns in a standard horizontal terminal printout.

What is the purpose of the ioctl system call in this context? What would be the limitations of your program if you only used a fixed-width fallback (e.g., 80 columns) instead of detecting the terminal size?
The ioctl system call using the TIOCGWINSZ request dynamically hooks into the active terminal session to retrieve its exact character width. If the program relied strictly on an 80-column fallback, the output would look broken on modern monitors. If a user expanded their terminal to full screen, the text would still wrap forcefully at 80 characters, wasting massive amounts of empty screen space on the right side. Conversely, if they shrank the terminal below 80 columns, the text would visually overflow and shatter the grid alignment.
